# 架构设计与系统边界

## 规则与 Agent 的取舍

时效、库存、风险分阈值属于确定性业务规则，优先使用可解释、可审计的规则引擎，而不是让大模型决定退款或冻结。大模型适合后续对客服对话、退款原因和商家备注做结构化分类，但输出仍应经过规则校验和人工复核。

## 一致性设计

- `inbound_events.event_id`：消息幂等；同 ID 不同正文拒绝处理。
- `exceptions.idempotency_key`：同一订单同类未解决异常只保留一张工单。
- `business_sequences`：在 PostgreSQL 事务中生成每日业务编号，与内部自增主键解耦。
- 异常、审计和 Outbox 同事务提交；外部飞书调用不占用订单事务。
- Outbox 由多 worker 使用 `FOR UPDATE SKIP LOCKED` 竞争消费，支持指数退避和死信状态。
- 已解决/拒绝的异常再次命中时重新打开；仍在处理中的重复命中只更新时间和版本。

## 安全边界

- 外部订单入口：HMAC、时间窗、防重放。
- n8n 内部入口：`X-Internal-Key`。
- 人工复核：`X-API-Key = REVIEW_API_KEY`。
- 规则和飞书初始化：`X-API-Key = ADMIN_API_KEY`。
- 所有密钥仅来自环境变量；仓库 `.env.example` 只有占位符。
- 本地 Compose 仅监听环回地址。公网部署必须补充 TLS、网关鉴权、限流和访问日志。

## 与真实平台的接口边界

仓库提供稳定的标准订单契约和 CSV 适配器，但不伪造淘宝、京东、抖店等平台连接。实际接入需要企业授权的开放平台凭证，并在独立适配器中完成平台验签、分页/游标、限流、字段映射和错误补偿。

## 系统验收方案

1. 从空数据库启动并检查 `/health/ready`。
2. 发送签名订单并展示一单命中多个异常。
3. 重放同一事件，证明异常总数与通知数不增加。
4. 并发发送订单，检查 `EXC-YYYYMMDD-NNNNNN` 无重复。
5. 暂时填错飞书配置，观察 Outbox 自动重试；恢复配置后再次投递。
6. 用错误和正确的复核密钥分别调用，展示鉴权与审计。
7. 解决异常后发送新事件，展示同一工单重新打开。
8. 检查 n8n 的异常/紧急分支、巡检批次汇总、运营日报和死信监控，确认 n8n 负责编排、API 负责事务一致性。

仓库内置脱敏订单数据用于安装验证与自动化回归。接入生产平台时，应使用企业正式授权的凭证，并按照接口边界实现对应平台适配器。
