# 业务验收方案

本方案使用可复现合成数据验证业务逻辑和故障边界。合成数据不代表任何企业的订单分布，测得结果只能描述本次实验环境，不能写成真实客户收益。

## 验收前提

- 使用隔离的 PostgreSQL 数据卷和测试飞书群；
- 固定生成器 `seed` 与 `as-of`；
- 输入是完整订单快照，`eventId` 在平台重试时稳定、业务状态变化时升级；
- 记录代码版本、机器配置、订单数量和测试时间。

## 核心场景

| 场景 | 输入 | 预期结果 |
|---|---|---|
| 正常订单 | 已发货、库存充足、低风险 | 无异常、无群通知 |
| 多异常叠加 | 72小时未发货、风险95、库存不足 | 同一订单产生3张不同类型工单 |
| 平台重试 | 同一 `eventId` 和相同正文重复发送 | 返回 `duplicate=true`，不重复建单或通知 |
| 事件冲突 | 同一 `eventId` 对应不同正文 | 返回 `409`，旧数据保持不变 |
| 重复巡检 | 新 `eventId`，异常条件不变 | 更新时间和版本，不重复发送即时通知 |
| 业务恢复 | 已发货或风险分降低的新完整快照 | 原异常自动转为已解决，记录审计并同步飞书 |
| 异常复发 | 已解决后再次满足规则 | 原工单重新打开并允许再次通知 |
| 并发复核 | 两人基于同一版本提交不同结论 | 第一人成功，第二人收到 `409` |
| 飞书不可用 | 错误凭证或超时 | 业务事务不回滚，Outbox 重试后进入死信 |
| 关闭通知 | 未启用日报/死信告警 | 任务返回受控关闭，不向群发送消息 |

## 合成数据

```bash
python scripts/generate_synthetic_orders.py \
  --count 1000 --seed 20260812 \
  --as-of 2026-08-12T12:00:00+08:00 \
  --output work/synthetic-orders.csv
```

保留输出首行、场景数量汇总和文件哈希，以便复现。`expectedExceptionTypes` 只用于核对识别结果。

## 建议记录的指标

- 订单处理成功率、异常识别一致率；
- 每秒处理订单数和 P50/P95 延迟；
- 重复工单数、重复即时通知数；
- Outbox 成功、重试、跳过和死信数量；
- 人工复核从接单到完成的时长；
- 发生版本冲突的次数；
- 自动恢复和人工解决的数量。

如果需要评估人工效率，应让实际操作人员使用相同订单集分别完成手工检查和系统复核，并如实记录样本量、参与人数与操作规则。
